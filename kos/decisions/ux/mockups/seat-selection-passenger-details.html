Terminal Signal — UX decision

Seat Selection + Passenger Details

One screen, branching on bus_class: a live seat map for reservable classes (aircon / deluxe / double-deck) or a seat-count stepper for ordinary. This is the screen carrying two of the product's "god moments" — a real seat grid with no signup wall (#1), and booking the whole family's names and seats in one uninterrupted pass (#2). Three layout options for the seat-map branch were compared below — Option B (Split Panel) was chosen: keeping the hold countdown, passenger fields, fare total and CTA always visible in a sticky panel outweighs the extra layout complexity, especially once the 1-hour hold is ticking. The seat-count (ordinary) branch doesn't vary meaningfully by layout, since it has no grid to arrange, so it's shown once at the end rather than three times.

Options considered — seat-map grid

Option A — Grid-First, List Below

Everything in one vertical column, in the order a rider actually does it: legend, deck toggle, seat grid, then a "Passengers" list that grows below the grid as seats are tapped. Simplest to build and the most natural single-column read on mobile — no split attention between two areas of the screen. Trade-off: on a long grid the passenger list and the CTA both sit below the fold until you scroll.

Option B — Split Panel (Sticky Booking Summary)

Grid on the left, a persistent "Your Booking" panel on the right that stays in view (sticky) while scrolling a long grid — the familiar e-commerce-cart / airline-seat-map pattern (Jakob's Law: lowest learning cost for anyone who's booked a flight). The hold countdown, passenger fields, fare total and CTA are always visible without scrolling back up, which matters once the 1-hour hold is ticking. Stacks to grid-then-panel, in that order, below lg.

Option C — Inline Seat-Anchored Capture

No separate "Passengers" section at all — tapping a seat expands a name field directly under that seat's row, inside the grid itself. The grid and the form are the same surface, so there's zero ambiguity about which name belongs to which seat (Gestalt proximity, taken as far as it goes). Trade-off: the grid reflows and grows taller as more seats are picked, which can feel jumpy past 3–4 selections — a real cost against the 6-seat cap this product allows.

Ordinary class — seat count (same for all three options above)

Whichever option above is picked, this stepper-driven variant is unaffected: it would sit in the same relative position (below the trip summary, above passengers) in Option A or C, or in the summary panel itself in Option B.

Implementation notes

  • Option B (Split Panel) chosen. Options A and C stay in the comparison above for reference, same as rejected options are kept (not deleted) elsewhere in this KOS. A laws-of-ux pass and any refinement/states work for Option B are deferred until a batch of mockups is ready for review, per this project's standing practice.
  • Seat grid shape is illustrative. BusUnit.seat_layout is a json column with no finalized shape yet — the 2+2 (aircon/double-deck) and 2+1 (deluxe) row/column/aisle conventions used here are a placeholder, not a decided schema.
  • Icon weight-per-state, adapted for tile size. iconography.md specifies Phosphor's armchair glyph at regular/fill/duotone weight to encode available/taken/premium. At 36–40px a tile needs to show its seat code to stay useful, so the weight language lives in the legend (bigger icons) while tiles carry state through color + border/fill only. Duotone violet is kept to the class badge rather than repeated per seat, since bus_class applies to the whole bus, not individual seats — there's no modeled "premium seat within a class" tier yet.
  • Held-seat timer kept deliberately simple. One persistent countdown line reflecting TripSeat.held_until (default 1hr, admin-configurable), not a per-tile timer or an animated ring — motion.md explicitly left this screen's countdown treatment open; this is the simplest option that still reads as urgent (warning color + icon + mono digits), same across all three layout options.
  • Deliberately out of scope for this pass: a real-time "this seat was just taken while you were deciding" collision state, inline field-validation errors, and a loading/submitting state. Deferred the same way trip-search-results.html's states are waiting on that file's option pick being finalized first — states get designed once an option is chosen, not across three unpicked options at once.
