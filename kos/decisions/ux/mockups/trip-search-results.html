Terminal Signal — UX decision

Trip Search Results

Three layout options for the results list a rider sees after submitting origin/destination/date — each trip must surface operator, class, fare and departure time. No option is picked yet; this is a comparison pass, same as the three Trip Search layouts were before Route Line was chosen. Pagination is cursor-based (next_cursor/has_more), so all three end in a "Load more" affordance rather than numbered pages.

Options considered

Option A — Manifest Row

One dense row per trip, like a physical departure manifest — operator and class on the left, time and fare in fixed mono-aligned columns, seats and CTA on the right. Fastest to scan when a route has many trips; each field collapses to a labeled stack below sm.

Option C — Timeline Rail

Trips anchored to a dashed vertical rail by departure time, grouped under Morning/Afternoon/ Evening — reuses the dashed-line motif from the chosen Route Line search screen for continuity. Makes time-of-day the primary read, ahead of operator or price.

Chosen

Pagination note: search stays single-day (origin/destination/date) for now, and the cursor orders trips strictly ascending by departure time — so Morning/Afternoon/Evening groups are guaranteed to appear at most once, in that order. "Load more" only ever appends rows below what's already rendered (client tracks the last-rendered bucket and only prints a new group header when it changes); a group header is never reopened or reinserted above already-rendered trips. Revisit if search ever stops being single-day — a later date's Morning trips would need a date label alongside the time-of-day bucket, appended as a new header rather than merged into the first one.

End of results

The cursor's has_more comes back false — every trip for this route/date is already on screen. The "Load more" button is replaced with a plain statement rather than left visible-but-disabled, so it reads as a completed list, not a stuck one (Peak-End Rule: the scroll should end on a clear, calm note). "Modify search" stays as the way out, same secondary-button treatment as the zero-results state on Trip Search.
