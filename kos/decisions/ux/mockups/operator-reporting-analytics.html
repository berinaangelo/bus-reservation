Operator Reporting/Analytics

Scope note: this is mvp-scope cut #7 ("build when operators start asking for it") — not committed for v1. Same forward-looking-preview handling as Rider Login and Platform Admin: flagged here, parked until real demand shows up, not a scope reversal.

All three options sit inside the already-chosen Sidebar + Table console shell — a new Reports nav item joins Routes/Trips/Bus Units/ Fare Rules/Manifest, nav chrome isn't re-litigated. What varies is how the main panel presents the report itself. Icons are Tabler, per iconography.md's operator-side rule. Demo data continues Victory Liner and its four routes from Operator Dashboard. Option C — Split Panel is chosen; A and B stay in the file for reference.

Options considered

Option A — Overview Dashboard (Stat Cards + Trend)

Landing view leads with headline KPIs (revenue, bookings, occupancy, avg fare) and a revenue trend chart, top-routes list below. Jakob's Law — this is the shape of nearly every analytics dashboard (Stripe, Shopify, Google Analytics) an operator has plausibly used before; the answer to "how's the business doing" is the first thing on screen, no filtering required. Peak-End Rule — echoes the "what's running today" framing already used for Option C — Overview Launcher, but for money/occupancy instead of resource counts.

Option B — Report Table (Filterable, Exportable)

No charts — a per-trip table (route, class, seats sold/total, occupancy, revenue) with a date-range + route filter bar and a CSV export, reusing the exact list-table shape every other console screen already uses. Jakob's Law — zero new visual vocabulary for staff who already scan Route/Trip/Bus Unit/Fare Rule tables daily; a spreadsheet-shaped report is also the format an operator's own back-office bookkeeping most likely already expects. Export ties directly to the streaming-vs-job-based export decision: a narrow date range streams inline (instant download); a full-history export queues a background job and the row appears in-page once ready — no email/SMS to rely on, since that's cut #2 too.

Option C — Split Panel: Filters Left, Report Right

A persistent filter/report-type panel pinned on the left (date range, route, class, report type: Revenue / Occupancy / Route Performance), the chosen report's chart + table renders on the right. Fitts's Law — same split-panel precedent as Seat Selection, Booking Lookup and Trip Manifest: filters never relocate while an operator tries several slices of the same date range in a row. Splits the difference between A and B — a chart for the at-a-glance read, plus the underlying table for the number an operator actually wants to quote or export.

States — Split Panel

Three states for the chosen Option C: switching the report type in the left panel, the right panel while a filter change is fetching new data, and a filtered slice that comes back with nothing to show.

Report switched — Occupancy

Clicking "Occupancy" in the left panel swaps the active row (Law of Similarity — same selected-state treatment as the console's own sidebar nav, one visual language for "this is the active thing" everywhere in the shell) and the whole right panel re-renders: headline number becomes the occupancy %, the table drops the Revenue column for Seats Sold/Total since that's what this report is actually about, and column order re-sorts by Occupancy instead of Revenue.

Triggered the instant any filter changes (date range, route, class, or report type). Ran the laws-of-ux pass over the whole batch and fixed 3 findings, all scoped to the chosen build-out since A/B are reference-only: the left panel's report-type list and its filter fields had no boundary between them beyond spacing (Law of Common Region) — added a divider, matching the sidebar's own convention for separating unrelated nav groups; the trend charts used three arbitrary bar-opacity levels with no legend explaining what they meant (Law of Similarity) — flattened to one shade plus a labeled "Today" bar, the one distinction that's actually real; and the Occupancy report's table bolded its own metric column in primary while the Revenue report's table left its equivalent column unstyled, an inconsistent treatment for the same role across the two reports — the Revenue column now gets the same emphasis.
