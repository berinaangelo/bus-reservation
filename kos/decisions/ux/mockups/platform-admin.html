Terminal Signal — UX decision

Platform Admin — Operator Onboarding

Scope flag: operator onboarding/approval is item #5 on mvp-scope.md's cut list — "build past roughly a dozen operators, once manual DB seeding stops scaling." Same situation as rider-login-booking-history.html: a forward-looking preview at the user's request, not a v1 commitment. For MVP, operators are still seeded directly in the DB by whoever runs the platform.

A new persona: PlatformAdmin — Terminal Signal's own staff, not an operator. Where OperatorStaff manage one operator's own fleet, this console sits one level above: reviewing bus companies that want to list trips on the platform, and approving or rejecting them before an Operator + first OperatorStaff account gets created. Icons follow the operator-side Tabler tier per iconography.md. Option A — Sidebar + Table + Drawer is chosen; B and C stay in the file for reference. CRUD forms, states (loading, empty queue, rejection reason), and the laws-of-ux pass stay deferred — this screen is a parked preview, not a committed build, so states aren't picked up unprompted the way they were for the primary-flow screens.

Options considered

Option A — Sidebar + Table + Drawer

The exact operator-dashboard.html shell reused wholesale — sidebar swaps Route/Trip/Bus Unit/Fare Rule for Applications/Operators, a pending-count badge sits on the sidebar item, and clicking a row opens the same slide-over drawer already built for Route/Trip/Bus Unit/Fare Rule CRUD. Jakob's Law, applied within-product — zero new pattern for anyone who already knows the operator console; the drawer's Approve/Reject footer is the only genuinely new surface.

Option B — Split Panel: Queue Left, Detail Right

Persistent two-pane layout, no drawer or modal — the same split-panel idiom already used for Seat Selection, Booking Lookup, Trip Manifest and Operator Login. Fitts's Law: Approve/Reject live in a fixed spot at the bottom of the right pane, so a reviewer working through several applications in a row never has to re-locate the action after each click — only the content above it swaps. Status filter tabs sit above the queue rather than as separate nav items, since it's one dataset viewed three ways, not three different resources.

Option C — Single-Column Expandable Card Feed

No sidebar, no split panel, no drawer — one scrollable feed of application cards, most recent first, each already showing enough to decide (contact, franchise no., permit link) with Approve/Reject right on the card. Justified by the queue's own expected size: mvp-scope's own rationale for cutting this screen is "past roughly a dozen operators" — this queue never holds more than a handful of rows even once built, so a triage IA built for high volume (A's drawer, B's persistent split panel) is solving a scale problem this screen won't actually have. Cards expand in place for the rare application needing a closer look (echoes Booking Lookup's reveal-in-place mechanic) rather than routing to a separate detail surface.
