Terminal Signal — UX decision

Trip Manifest

The operator-side screen where OperatorStaff check riders in at boarding — the physical-world event underneath god moment #4 (no paper, no queue, the moment that decides whether a rider books digitally next time) and #6 (the manifest fills itself in live instead of a phone log). Two things distinguish this screen from every CRUD table already built for Operator Dashboard: bookings land in real time while staff are looking at it (a rider can complete checkout on their phone seconds before boarding), and the primary action isn't edit/delete — it's check this specific person in, fast, over and over, during a boarding rush. Staff resolve a passenger the same way they resolve a lookup at the counter: by reference_code, hand-typed. All three options below sit inside the already-chosen Sidebar + Table console shell — Manifest is already a stubbed nav item there — so the nav chrome isn't being re-litigated; what varies is the check-in interaction pattern in the main panel. Demo trip continues the JoyBus double-deck / ₱950 booking from Seat Selection — the Maria & Jose Santos family booking (4XK-7QM-9) is still on this bus. Option A — Roster Table + Quick Check-in Bar is chosen; B and C stay in the file for reference. Per payment-method, this screen is also where Payment.status flips pending_cash→collected — Option A now includes the Paid toggle next to check-in.

Options considered

Option A — Roster Table + Quick Check-in Bar

Extends the exact list/table shape already established for Route/Trip/Bus Unit/Fare Rule. Jakob's Law — staff are already trained on this shape from every other screen in the console, one row down in the same sidebar. Fitts's Law — the reference_code check-in field lives in one fixed bar pinned above the table, so the repeated counter motion (type code, hit Check In, next passenger) never has to hunt row-by-row down a scrolling list.

Paid toggle flips the underlying Payment record's status (pending_cash→collected), not the seat row — a multi-seat booking shares one Payment, so 5A/5B above share one toggle state; 5B's control is shown disabled/mirrored rather than as a second independent switch, so staff can't record the same cash twice under one reference_code. Option B — Seat-Map Mirror + Check-in Panel

Reuses the literal seat grid from Seat Selection — same tile size, same A/B | C/D layout, same Lower/Upper deck toggle — so "Seat 5A" means the identical physical seat to staff that it meant to the rider who booked it. Law of Similarity / Jakob's Law-echo — boarding progress reads at a glance across the whole bus (a wall of green means done) instead of scanning a list row by row. Tapping a seat reveals its passenger inline, mirroring the same tap-to-reveal mechanic [[seat-selection]] already used for passenger-name capture (no separate step, Doherty Threshold).

Ordinary-class trips (GL Trans / ₱480, no reservable seats) have no grid to mirror — same duality as Seat Selection. The manifest for those falls back to a plain checked-in/total counter with the roster as a flat list, not built out here since it doesn't vary by layout option. Open note: "Booked · awaiting boarding" is a new use of the accent color role — color-scheme.md didn't define this state; flagging rather than quietly inventing a 7th role.

Option C — Split Panel: Live Roster + Check-in Detail

Same split-panel shape already chosen for Seat Selection and Booking Lookup: a persistent check-in form pinned on the right, a live-updating roster on the left. Fitts's Law — during a boarding rush the check-in field never relocates on screen between passengers, so staff's hand and eyes make the same short trip dozens of times in a row. New arrivals surface as an unread count rather than interrupting the field staff is typing into.
