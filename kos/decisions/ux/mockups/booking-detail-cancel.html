Booking Detail / Cancel

The full-page destination a rider lands on after finding or opening a specific booking — from booking-lookup.html's found panel, or a "Manage Booking" link off e-ticket-confirmation.html. Same god moment #5 (no login, reference_code + contact number is the account system) carried to a full detail view, with the same simple-cancel capability: void + release seat, no refund automation. Option C — Status Banner, Stacked Sections is chosen, full build-out, states and variants below.

Single centered column, same ticket-stub shape as e-ticket-confirmation.html: reference-code hero, dashed tear, trip/passenger/fare blocks, danger-outline Cancel below the tear. Jakob's Law — the rider already saw this exact shape right after paying; returning here to manage the booking is free to parse.

Option C — Status Banner, Stacked Sections

Chosen

Full-width colored status banner at top, then stacked bordered sections (trip, passengers, reference/fare), cancel pinned in a bottom action bar. Gestalt grouping via section borders — status, trip, passengers and fare each read as their own scannable block instead of one dense card. Echoes the Timeline Rail rhythm of Trip Search Results, so the visual language stays consistent across the booking flow.

Implementation notes

  • Void + release-seat-only, no refund automation. mvp-scope.md keeps refund automation and any cancellation/fare audit trail out of scope for v1 — the cancelled copy here is deliberately honest about that ("no refund is issued automatically"), not vague.
  • This screen assumes prior verification, not raw access by reference code alone. Per god-moments.md #5, reference_code + contact number is the account system for v1 — this detail page is the destination after that pair is checked (booking-lookup.html), not a second place to re-enter it. A direct link (e.g. bookmarked URL) should still require that verification before rendering real booking data.
  • Cancel is a mutating, double-tap-prone action with no documented server-side idempotency key. payment-idempotency.md only covers checkout/payment submission. The inline confirm-step here is a UX guard against a double-tap, not a substitute for a real idempotency decision on the cancel endpoint — flagging as an open gap, not resolving it in this mockup.
  • Cancelled-state copy is reused verbatim from the decided wording in booking-lookup.html's cancelled end-state, extended here to name every released seat rather than just one.
  • Reference code format and timestamps follow reference-code-format.md (grouped XXX-XXX-C) and utc-storage-ph-display.md (UTC stored, Asia/Manila displayed) — no new conventions introduced.
  • Fare figures are minor-units-derived display, never raw integers — money-as-minor-units.md.
  • Option C (Status Banner, Stacked Sections) chosen. Options A and B stay in the comparison above for reference, not deleted, same convention as every prior screen. A laws-of-ux pass is deferred until this batch of mockups is ready for review, per this project's standing practice.
