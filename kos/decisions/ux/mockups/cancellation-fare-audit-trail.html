Terminal Signal — UX decision

Cancellation / Fare Audit Trail

Scope flag: the cancellation/fare audit trail is item #8 — last — on mvp-scope.md's cut list: "build on an actual dispute or LTFRB audit engagement." Same situation as platform-admin.html and operator-reporting-analytics.html: a forward-looking preview at the user's request, not a v1 commitment. For MVP, a cancellation is just a void + seat release with no logged reason, and a fare change is just a new effective-dated FareRule row with no record of who added it or why.

What this screen is actually for: when a rider disputes a cancellation, or LTFRB asks an operator to justify a fare change, someone needs to answer who did what, when, and why — not just what the current state is. That's a different shape than the CRUD screens already built: it's read-only, append-only (an audit log that could itself be edited isn't an audit log), and organized around two source events — a Booking being cancelled, and a FareRule being added or changed — rather than around a resource you manage. Sits inside the already-chosen Sidebar + Table operator console shell from operator-dashboard.html as a new nav item; only the main-panel log pattern varies below. Per mockup-choice-is-users.md, presented neutrally — no option picked yet.

Options considered

Option A — Merged Log Table + Detail Drawer

One reverse-chronological table, every cancellation and fare change interleaved by timestamp, with a type badge distinguishing rows. Clicking a row opens the same slide-over drawer already built for Route/Trip/Bus Unit/Fare Rule CRUD. Jakob's Law, applied within-product — zero new interaction pattern for operator staff; the drawer's read-only before/after diff is the only new surface. Best when an auditor asks "show me everything that happened to this operator in March," since nothing is pre-split by type.

Option B — Split Panel: Filters Left, Timeline Right

Persistent filter panel (date range, action type, actor, target search) on the left; a vertical timeline rail on the right, entries grouped by day and expanding inline on click rather than a drawer — echoes the Timeline Rail concept from trip-search-results.html. Fitts's Law — the filter panel never relocates while narrowing a date range for a specific dispute, same split-panel precedent as Seat Selection/Booking Lookup/Operator Reporting. Best when the actual task is "narrow down to the one incident," not "scan everything."

Option C — Two-Tab Flat Tables (Cancellations / Fare Rule Changes)

Cancellations and fare changes don't share meaningful columns — a cancellation needs passenger/seat/refund-status, a fare change needs old-fare/new-fare/effective-date. Merging them (Option A) forces either blank cells or a cramped generic "details" column. Hick's Law — a tab switcher keeps each table's columns purpose-built and scannable, closest to how an auditor actually asks: "show me all cancellations in this range," not "show me a mixed feed."

Notes for the pick

A (Merged Log) is the lowest-effort build — one table, one new drawer variant, reuses everything from the operator console shell. Weakest at narrowing a specific dispute down (no filters shown, though they could be added to the header).

B (Filters + Timeline) is the strongest fit for the actual stated trigger — "an actual dispute or LTFRB audit engagement" is a narrow-down task, not a scan task — but is the most new surface area (a timeline rail component doesn't exist yet anywhere in the system).

C (Two-Tab Tables) gives the cleanest data model per type and the most direct CSV export (each tab is already the exact shape LTFRB or a rider's bank would want handed to them), at the cost of losing a single combined view across both event types.

Recommendation: C, if this stays a compliance/export-first tool for occasional real disputes. B, if staff will actually work inside this screen regularly to investigate. Not recommended to build any of the three before a real dispute or LTFRB engagement actually happens, per the mvp-scope cut rationale.
