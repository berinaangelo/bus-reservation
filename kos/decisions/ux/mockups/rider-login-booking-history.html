Terminal Signal — UX decision

Rider Login + Booking History

Not scheduled for the current build. Rider accounts are explicitly cut for v1 — guest lookup via reference_code + contact number (see booking-lookup.html) is the v1 "account system." This file is a forward-looking preview only, kept for when repeat-booking volume makes search-from-scratch costly enough to justify it. It's designed to sit alongside guest lookup, not replace it — a rider who never logs in can still always find a single booking by code. Option B — Split Panel: Account Left, History Right is chosen below, badged the same way as every other screen's pick; Options A and C stay in the file for reference.

Open dependency, not solved here: all three options below use phone number + SMS one-time code instead of email/password — it reuses the contact number already collected at booking and avoids inventing a password-reset flow. But SMS/email notifications are also cut for v1 (mvp-scope #2), and OTP delivery needs that same SMS provider integration. This mockup can't ship before that dependency does, even if rider accounts get greenlit on their own.

Options considered

No option is picked yet — presented neutrally, exploration only.

Option A — Single-Column Stacked

Log in on top, history reveals below in the same column — the same reveal-in-place mechanic as Booking Lookup's Option B. Jakob's Law: the plainest, most-recognized "sign in → see your list" shape, no new pattern to learn. History renders as a flat list of row cards, matching Trip Search Results' Manifest Row idiom.

Option B — Split Panel: Account Left, History Right

Persistent account panel (phone number, log out, quick counts) beside the list, with Upcoming/Past tabs above the list itself. Same split-panel idiom already used for Seat Selection, Booking Lookup, and Operator Login — Jakob's Law, applied within-product. Hick's Law: two tabs, not a status filter dropdown, since Upcoming vs. Past is the only split a rider actually needs day-to-day.

Option C — Hero Next Trip + Grouped Timeline

Login collapses to a thin top strip once authenticated; the next upcoming trip renders as an oversized ticket-stub hero card (echoes E-Ticket Confirmation's aesthetic), with past bookings below grouped under a lighter-weight timeline. Peak-End Rule: leads with the one thing a returning rider actually opened the app to check — "when's my next bus" — rather than treating every booking as equally prominent.
